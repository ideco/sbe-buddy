# Map an existing XML schema

Use schema-first mode when you have an SBE XML schema that your Java
declarations need to match. The compiler checks those declarations against
the XML, then generates flyweights and record codecs from it.

You need to declare the whole schema in Java, including every message and
named type. You cannot select only the messages or fields your application
reads. Fields that your records do not carry must still be declared as
[unmapped members](../../glossary.md#unmapped-member); groups and
variable-length data must have record components.

This guide assumes a Maven project with sbe-buddy's annotation processor
configured. The [first-message tutorial](../tutorials/getting-started.md)
provides that setup. The example below uses its `PlaceOrder` message; for
your own schema, substitute its package, declarations and attributes.

## 1. Add the XML as a resource

Place the schema at
`src/main/resources/com/example/trading/trading.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sbe:messageSchema xmlns:sbe="http://fixprotocol.io/2016/sbe"
                   package="com.example.trading"
                   id="100" version="0" headerType="messageHeader">
    <types>
        <composite name="messageHeader">
            <type name="blockLength" primitiveType="uint16"/>
            <type name="templateId" primitiveType="uint16"/>
            <type name="schemaId" primitiveType="uint16"/>
            <type name="version" primitiveType="uint16"/>
        </composite>
    </types>
    <sbe:message name="PlaceOrder" id="1">
        <field name="orderId" id="1" type="int64"/>
        <field name="quantity" id="2" type="int32"/>
    </sbe:message>
</sbe:messageSchema>
```

Maven copies resources to the compile classpath before running the
annotation processor, so no additional resource configuration is needed.

If you are starting from a schema generated by sbe-buddy, copy
`target/classes/com/example/trading/schema.xml` to this resource location
before cleaning the build. Keep the resource under version control.

## 2. Point the package at the resource

Create or update `src/main/java/com/example/trading/package-info.java`:

```java
@SbeSchema(id = 100, version = 0, resource = "trading.xml")
package com.example.trading;

import net.concini.sbebuddy.SbeSchema;
```

The Java package must match the schema's `package` attribute. The resource
name is relative to that package: `"trading.xml"` resolves to
`com/example/trading/trading.xml` on the classpath. A leading slash makes
the name absolute, so `"/com/example/trading/trading.xml"` selects the same
resource.

Declare the schema's other attributes when they differ from the annotation
defaults. For example, an XML `description` needs a matching `description`
on `@SbeSchema`. This schema uses the standard message header supplied by
sbe-buddy, so it needs no separate Java header declaration.

## 3. Declare the matching message

Create or retain `src/main/java/com/example/trading/PlaceOrder.java`:

```java
package com.example.trading;

import net.concini.sbebuddy.SbeField;
import net.concini.sbebuddy.SbeMessage;

@SbeMessage(id = 1)
public record PlaceOrder(
        @SbeField(id = 1) long orderId,
        @SbeField(id = 2) int quantity) {}
```

These declarations match the message name, template ID, field names, field
IDs, types and order in the XML. The Java numeric types select `int64` and
`int32` just as they do in code-first mode.

For a larger schema, continue until every message and type is represented.
Use `name` when a Java name differs from the schema name. For fields that
use named types, declare those types and reference them in the annotations.
The XML does not fill in missing Java declarations or select a field's type
for you.

## 4. Compile and resolve differences

From the project directory, run:

```sh
mvn clean compile
```

A successful build generates `PlaceOrderCodec` and the SBE flyweights, just
as in the tutorial. The resource is copied to
`target/classes/com/example/trading/trading.xml`. sbe-buddy uses it for
generation without rewriting it or producing a separate `schema.xml`.

If the declarations differ, compilation fails. For example, declaring
`quantity` as a `long` selects `int64`, while this XML requires `int32`.
The diagnostic includes:

```text
the schema has type="int32", not "int64"
```

Correct the Java declaration to match the schema and compile again. Also
check metadata such as descriptions, semantic types and versions when a
diagnostic points to an attribute: these are part of the comparison too.

Use `mvn clean compile` after editing the XML, including when no Java source
changed. A resource change alone may not cause Maven to recompile the
declarations, so a clean build ensures the comparison runs.

If you are using the tutorial's `Example.java`, run it with:

```sh
mvn exec:exec
```

It should still print the decoded order and `Equal: true`. Application code
uses the same codec API in either mode.

For when to choose each mode and what a successful comparison guarantees,
see [Code-first and schema-first](../concepts/code-first-and-schema-first.md).
