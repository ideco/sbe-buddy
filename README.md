# sbe-buddy

Code-first Simple Binary Encoding for Java.

Define an SBE schema as annotated Java:

```java
// package-info.java
@SbeSchema(id = 100, version = 0)
package com.example.trading;
```

```java
@SbeMessage(id = 1)
public record PlaceOrder(
    @SbeField(id = 1) long accountId,
    @SbeField(id = 2) int quantity,
    @SbeField(id = 3, primitiveType = UINT16) int venue,
    @SbeField(id = 4) Side side) {}

@SbeEnum(primitiveType = UINT8)
public enum Side {
    @SbeEnumValue("0") BUY,
    @SbeEnumValue("1") SELL
}
```

Compile it and sbe-buddy generates the normal SBE flyweights:

```
com.example.trading.sbe.PlaceOrderEncoder
com.example.trading.sbe.PlaceOrderDecoder
```

They are generated by SBE's own `JavaGenerator`.

sbe-buddy writes the SBE XML schema the annotated Java describes and hands
it to sbe-tool, which parses it, builds the IR and generates the flyweights.
The schema and the wire representation are the same as if you had written
that XML by hand, and the XML ships in your jar as
`com/example/trading/schema.xml`, so sbe-tool's other generators produce
the same messages for C, C++, C# and Rust.

## Why

SBE's flyweights are exactly what you want when allocations matter: they
work directly on the encoded buffer and add very little between your code
and the wire.

The part that tends to age less gracefully is maintaining the same message
in both an XML schema and the Java model the rest of the application works
with.

sbe-buddy makes the Java declaration the schema while keeping SBE's
generated code and runtime model intact.

It is not another SBE implementation. It is another way to describe an SBE
schema.

## The schema stays explicit

Wire compatibility should not depend on declaration order or hidden state.

Ids and wire types remain explicit:

```java
public record Order(
    @SbeField(id = 1) long orderId,
    @SbeField(id = 2, primitiveType = UINT16) int venue) {}
```

Enums have explicit values:

```java
@SbeEnum(primitiveType = UINT8)
public enum Side {
    @SbeEnumValue("0") BUY,
    @SbeEnumValue("1") SELL
}
```

The one default is the same-width signed type for a bare Java primitive:
`long` is `int64` unless you say otherwise. Unsigned types, `char`, named
types and schema versions are always written down.

Invalid combinations fail during compilation, at the declaration that
caused the problem.

There is no auto-numbering and no lockfile.

## SBE is still SBE

sbe-buddy follows SBE's schema model rather than inventing a parallel one.
One annotation per element of `sbe.xsd`, one member per attribute, with
the XSD's names:

```
<messageSchema>  → @SbeSchema on package-info.java
<message>        → @SbeMessage on a record
<field>          → @SbeField on a record component
<group>          → @SbeGroup on a List<E> of a record
<data>           → @SbeData on a String or byte[]
<type>           → @SbeType
<composite>      → @SbeComposite on a record
<ref>            → @SbeRef
<enum>           → @SbeEnum on a Java enum, @SbeEnumValue on each constant
<set>            → @SbeSet on a Java enum, @SbeChoice on each constant
```

Named types matter here. In SBE, a named type and its underlying primitive
may encode to the same bytes while still producing a different schema.

So the aim is not merely byte compatibility. The Java form describes the
same SBE schema, and the XML in the jar proves it.

## Generated code

For each message, sbe-buddy generates the same encoder and decoder you
would get from sbe-tool:

```java
MutableDirectBuffer buffer = new UnsafeBuffer(new byte[256]);
PlaceOrderEncoder encoder = new PlaceOrderEncoder();
encoder.wrapAndApplyHeader(buffer, 0, new MessageHeaderEncoder())
    .accountId(42)
    .quantity(100)
    .venue(7)
    .side(Side.BUY);
```

And on the other side:

```java
PlaceOrderDecoder decoder = new PlaceOrderDecoder();
decoder.wrapAndApplyHeader(buffer, 0, new MessageHeaderDecoder());
long accountId = decoder.accountId();
int quantity = decoder.quantity();
```

There is no wrapper around this generated code today. You are using SBE's
own flyweights.

## How it works

The annotation processor is a small compiler pipeline:

```
annotated Java
      ↓
 schema model
      ↓
  validation
      ↓
  XML schema
      ↓
   sbe-tool
      ↓
SBE flyweights
```

The interesting boundary is the XML.

sbe-buddy owns the translation from Java declarations to the SBE XML
schema and the rules a schema must satisfy. Once that document exists,
sbe-tool takes over: it validates, parses, builds the IR and generates.

This keeps the wire-level implementation where it already belongs, and it
means nothing with wire semantics, no offset, no null value, no flyweight
method name, is computed here.

## Compatibility

The tests hold a hand-written SBE XML schema for every feature `sbe.xsd`
can express, and one for the example module.

CI checks that the annotated Java form produces a schema equivalent to the
hand-written one, and that sbe-tool accepts the hand-written one without an
error or a warning.

That gives a useful definition of correctness: changing how the schema is
written must not change what SBE sees.

## Current scope

sbe-buddy is early.

Today it takes annotated Java through the processor to the XML schema in
the jar and SBE's encoder and decoder flyweights, for everything `sbe.xsd`
can express:

* primitives, unsigned types and `char`
* fixed-length arrays and named types
* composites and refs
* enums and sets
* groups and var-data
* constants and optional presence
* schema evolution: `sinceVersion`, `deprecated`, `semanticVersion`
* byte order and custom header types

What it does not do yet is map your records to those flyweights. A generated
codec between the record and the generated encoder and decoder, with `null`
for absence and bindings for domain types, is the next thing being built.

See [docs/intent.md](docs/intent.md) for where the project is going.

## Setup

Requires JDK 21.

Put `sbe-buddy-api` on your compile classpath and `sbe-buddy-processor` on
javac's annotation processor path. Nothing is published to a repository
yet, so build and install both from a clone first:

```
./mvnw install
```

Then, in Maven:

```xml
<dependency>
  <groupId>net.concini</groupId>
  <artifactId>sbe-buddy-api</artifactId>
  <version>0.1.0</version>
</dependency>
```

```xml
<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <annotationProcessorPaths>
      <path>
        <groupId>net.concini</groupId>
        <artifactId>sbe-buddy-processor</artifactId>
        <version>0.1.0</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
```

The api brings Agrona, which the flyweights compile against. Compiling needs
no JVM flag. Running the flyweights does, in every JVM that loads an Agrona
buffer, tests included:

```
--add-opens java.base/jdk.internal.misc=ALL-UNNAMED
```

## Building

```
git clone --recurse-submodules https://github.com/ideco/sbe-buddy.git
cd sbe-buddy
./mvnw verify
```

JDK 21, and nothing else: the wrapper fetches Maven.
